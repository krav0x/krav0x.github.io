Portuguese Accounting RAG

WIP, retrieval baseline shipping

Portuguese-language RAG assistant over Portugal's core tax and accounting corpus (CIRS, CIRC, CIVA, RITI, LGT, EBF, SNC, NCRF). 4,448 article-level chunks embedded once with multilingual-e5-large, stored in Chroma, queried via Llama-3.3-70B on Groq. The prompt hard-codes three rules: answer only from retrieved context, cite the specific article, refuse otherwise. Retrieval iteration moved recall@5 from 57.1% to 66.7% on a 25-question held-out eval; 100% refusal accuracy on the 4 refuse-worthy questions; 9.5% hallucination rate on the baseline. Tier-1 (read-only lookup) only in the current build.

Case study

Context

Practising Portuguese accountants and small-business owners keep asking the same class of question: "which article covers this?", "what's the rate on X?", "how is Y treated for VAT?". The correct answers live in a few thousand pages of primary legislation (Códigos, Decretos-Lei, NCRF standards) that a general-purpose LLM will happily paraphrase from memory, often with a confident but wrong article number. The bar this project sets for itself is narrower than "an accountant in a box": produce an answer in European Portuguese that is (a) traceable to a specific article of a specific code and (b) explicitly refuses when the retrieved context doesn't support the question, so the user knows to escalate instead of trusting a fabrication.

Approach

Single-tier RAG, deliberately kept simple:

  • Knowledge layer, RAG. Primary legislation is chunked article-by-article for the tax codes (Artigo N.º boundary regex) and by recursive character splitting for the accounting standards (NCRF, EC, NI, SNC), which don't follow a strict article structure. Chunks are embedded once with intfloat/multilingual-e5-large and stored in a persistent Chroma collection.
  • Behaviour layer, prompt only. No LoRA. The behaviour of the assistant (answer in European Portuguese, only from retrieved context, cite the article, refuse otherwise) is enforced entirely in the system prompt. A LoRA pass was scoped but not run; the choice was to see how far a strong instruction-tuned base could go on a well-chunked corpus before spending on adapter training.
  • Computation layer, none yet. The current build does no deterministic numeric computation. Questions that ask "how much would I pay" are treated as refusal cases and pushed back to the user with a "consult a certified accountant" recommendation.

Autonomy tiers. The design target is three tiers: (1) read-only lookup, (2) draft-and-review with a human accountant approving, (3) prepare-for-submission with structured outputs for AT portals. The current build only implements tier 1; the eval below is scored against that scope. Tiers 2 and 3 are the next iteration and out of scope for these numbers.

Model choice. Groq-hosted Llama-3.3-70B-Instruct in the app, chosen for cost (free tier), speed, and adequate multilingual quality in European Portuguese. The evaluation was run against the same model via the Hugging Face inference router when Groq credits ran out; same weights, so answer quality is directly comparable. The latency numbers reflect the HF router path and would be lower on Groq.

Engineering notes

  • Hybrid chunker. split_by_article_strict uses a (?i)(Artigo\s+\d+\.º(?:-[A-Z])?) regex on the tax codes (CIVA, CIRC, CIRS, LGT, RITI, EBF, SNC) so every chunk is one legal article with its number in the chunk id ("CIVA - Artigo 18.º"). NCRF, EC, NI use a 1000/100 recursive splitter because those documents don't have article-level structure. This is what makes citations traceable: the retrieved chunk id is the citation.
  • Multilingual embedding choice. intfloat/multilingual-e5-large was picked over Portuguese-only encoders because the corpus mixes technical Portuguese (legislative style), abbreviations (IRS, IVA, PPR), and code numbers. E5-large was empirically better at surfacing the correct article across the eval set than smaller multilingual MiniLM variants tested locally.
  • Retrieval-tight prompt. The prompt hard-codes three rules (answer only from context, refuse otherwise, respond in European Portuguese). The initial eval showed this doing real work: every one of the 4 refusal-worthy questions produced a proper refusal, and the model correctly refused on retrieval misses instead of hallucinating a number (with two soft-hallucination exceptions covered in Failure modes below).
  • Streamlit UI with citation panel. Every answer ships with a "View Sources / Legal Basis" panel that dumps chunk id and a 300-character preview per retrieved doc, so the user can verify the citation without leaving the tab.
  • What is not in there. No LangGraph, no agentic tool use, no LoRA, no query decomposition. Those are candidates for later iterations; none are implemented today, and I would rather be measured on what is shipped than on what is planned.

Evaluation setup

25-question held-out eval set: 18 single-source factual lookups, 3 cross-source questions that require chunks from two codes, 4 refusal-worthy questions (personal legal advice, personalised numeric computation, post-cutoff regulatory data, cross-border tax planning). Ground-truth citations are stored per question in evals/eval_set.json; a lightweight harness (evals/run_eval.py, evals/eval_retrieval.py) queries the live Chroma store, runs the same prompt the app uses, and auto-grades each answer.

Auto-grader rubric (a proxy for hand-grading, not a substitute):

  • Retrieval hit @k. The expected article id appears as a substring of any retrieved chunk id in the top-k.
  • Answer accuracy. The answer contains at least min_keyword_hits of the pre-declared correctness keywords (e.g. "23 %" for the VAT-rate question, "lucro tributável" for the IRC-base question).
  • Hallucination. The answer cites an Artigo N.º that does not appear in any of the retrieved chunks fed to the LLM.
  • Refusal correctness. For the 4 refuse-questions, the answer matches one of the refusal-phrase patterns.

Outcome

Rather than shipping a first-pass baseline and calling it done, retrieval was iterated on because it caps everything downstream. Every row below is a real, reproducible run of evals/eval_retrieval.py against the eval set.

+9.6 points of recall@5 vs the v1 baseline, the metric that actually decides whether the LLM sees the correct article.

What each iteration changed:

  • v2, E5 prefixes on both sides. intfloat/multilingual-e5-large was trained with "query: " in front of queries and "passage: " in front of documents; the original ingest embedded both raw. Re-indexing with the "passage: " prefix and prepending "query: " at retrieval time is a documented free lift. Result: +5 pts on @1 and @3, roughly neutral at @5. Not a game-changer alone, but a prerequisite for later iterations.
  • v3, source-tag headers in the embedded text. The chunker was writing the source name (CIVA, CIRC, CIRS) into chunk metadata, but not into the embedded text. A query mentioning "IRC" had no lexical anchor to the CIRC chunks; it had to match through semantics alone, and dense retrieval kept returning CIRS articles for IRC questions. Fix: prepend "[CIVA] CIVA - Artigo 18" to each chunk's text before embedding. Result: +9.6 pts of recall@5, the single biggest win of the iteration.
  • v4, over-eager dedup (backed out). Inspection revealed a shocking amount of chunk duplication: CIVA-Artigo 2 was fragmented into 141 chunks, CIVA-Artigo 3 into 109, because the PDFs open with a full table of contents (every article title listed) and inline-reference each article dozens of times. First attempt: keep only the longest fragment per article. Result: retrieval collapsed, recall@5 dropped to 38.1% because the longest fragment often wasn't the one carrying the answer (e.g. for CIVA-18, the longest fragment contained the rules for grouped-goods bundles; the actual rate table with 23% was in a different fragment). Reverted.
  • v5, filter, don't dedup (kept). Kept multiple fragments per article, but dropped chunks that were mostly "............" dot-leaders (TOC entries) or shorter than 120 non-dot characters. Corpus went from 4,448 to 3,211 substantive chunks. Result: matched v3 at @5 (66.7%) with a cleaner corpus and a clearer story about what got dropped and why.
  • BM25 hybrid (tried, didn't ship). Portuguese legal text saturates BM25 with high-frequency generic phrases ("sujeitos passivos", "matéria coletável", "taxa") that appear in nearly every article. RRF fusion at four different dense/sparse weightings; none beat dense-alone. Kept the code as a reference implementation.
  • Cross-encoder reranking (tried, didn't ship). BAAI/bge-reranker-v2-m3 over a pool of 30 dense hits. Gave +5 pts at recall@1 but hurt @3 and @5 (the reranker sorted the pool aggressively toward the very top, which helped exact hits but hurt broader coverage). On CPU it also added ~38 s per query, a non-starter for a Streamlit tool. Kept as a reference for the day this runs on GPU.

Failure modes and confounds

Six of the 21 non-refuse questions never enter top-10 across any tried config:

  • Q02. "Qual é a taxa geral do IVA em Portugal continental?" (target CIVA-Artigo 18).
  • Q03. "Qual é a taxa geral do IRC aplicável a sujeitos passivos residentes?" (target CIRC-Artigo 87).
  • Q12. "Em que consiste o regime do IRS Jovem?" (target CIRS-Artigo 12-B).
  • Q17. "Como se determina o lucro tributável em sede de IRC?" (target CIRC-Artigo 17).
  • Q19. Cross-code (CIRS-31 + CIRC-17).
  • Q20. Cross-code (CIVA-3 + CIRC-23).

Manual inspection confirmed the answer text is in the corpus: CIVA-18 fragment #4 literally contains "a taxa de 23 %"; CIRC-87 fragment #3 literally contains "A taxa do IRC é de 17 %". Dense retrieval isn't finding them because the queries use paraphrases the chunks don't contain. "taxa geral" and "sujeitos passivos residentes" in the query semantically match articles about regime geral and residência fiscal, not the rate table. That is a query-side problem, not a retriever-side one.

There is also an upstream PDF-extraction issue: for a few CIVA articles, PyMuPDF loses the multi-column rate tables entirely, leaving literal "1 - ... 2 - ..." dot-leaders where the tax rates should be. That is a floor on retrieval quality no amount of encoder tuning can lift.

Confounds worth stating out loud:

  • n=25 is small. A real portfolio-grade eval wants 100+ items with inter-annotator agreement on the ground-truth citations.
  • Keyword auto-grading misses correct paraphrases. Q08's answer identified sujeitos passivos correctly by describing the mechanism, but scored only 1/2 keyword hits because it didn't use the literal phrase "atividade económica".
  • I graded my own eval. A stronger judge model (Claude Sonnet or GPT-4-class) run as an LLM-as-judge would give a more defensible answer-accuracy figure. The retrieval and refusal numbers, which don't depend on the grader, would not move.
  • Ground truth had to be corrected mid-run. Q03 and Q04 originally expected "21%" and "17%" for the IRC rates, but the actual PDFs cite Lei n.º 64/2025 which sets the general IRC rate to 17% and the first-50k rate to 15%. The eval was updated to match the corpus. This is a good example of why an assistant that refuses a memorised answer is more valuable than one that confidently recites an out-of-date figure.
  • Only one base model was evaluated. The plan originally scoped Amália (EuroLLM-9B) and EuroLLM-22B as an A/B; neither is wired up in the current build, so there is no delta to report.

Roadmap

Retrieval iteration got recall@5 from 57.1% to 66.7% and identified the exact remaining failure mode. Portfolio-shippable target is ≥80% recall@5. Two concrete levers, in priority order:

  • Query rewriter. A small LLM step that reformulates the user's question into 2 or 3 lexical variants and OR-s the results. E.g. "taxa geral do IVA" also tries "taxas do imposto" and "IVA continente". Best guess: +10 to 15 pts of recall@5. Cost: one small Groq call per user question, still well within free tier.
  • PDF extraction pass. Swap PyMuPDF for pdfplumber with a table-aware extractor to recover the CIVA rate tables that currently show up as dot-leaders. This lifts a floor rather than a ceiling; it doesn't help most questions, but the ones it helps are unrecoverable today.

Longer-horizon, in order of expected value:

  • AT circulars and OE annual updates in the corpus, with a per-chunk validity date so refusals can be precise ("a informação sobre 2026 ainda não está indexada").
  • Tier-2 autonomy path: a draft-a-reply mode where the assistant produces a structured citation table (article, quote, my interpretation) that a human accountant can approve or reject.
  • Grow the eval to 100 items and run under an LLM-as-judge with a stronger reference model, plus a small A/B against EuroLLM-9B on the same set.

Base model (app and eval): Llama-3.3-70B-Instruct, temperature 0.1. Served via Groq in the app, via HF inference router in the eval. Embedding: intfloat/multilingual-e5-large, run locally on CPU. RAG store: ChromaDB, persistent on disk, ~47 MB per index. Framework: LangChain (langchain_chroma, langchain_huggingface, langchain_groq, langchain_text_splitters) for the retrieval and prompt-templating glue; PyMuPDF (fitz) for PDF extraction. Portuguese-language notes. UI and prompts use PT-PT throughout (declaração, coleta, matéria coletável, sujeito passivo, isenção, tributação autónoma), not the Brazilian variants a general LLM would default to. The chunker preserves the ordinal marker (Artigo 68.º) so the retrieved citation reads correctly in the legal-Portuguese convention. The refusal path is phrased as a formal recommendation ("recomendo consultar um contabilista certificado") rather than a shrug, so the assistant fits the register a Portuguese small-business user expects.

SAF-T PT Invoice Analysis

Shipped, used by my practice

Bulk parser and reconciliation tool for Portuguese fiscal SAF-T files, in production across 2 retail chains and 6 stores. Streams a ~50 MB monthly file (about 15,000 invoices, 55,000 line items) client-side in a Web Worker and parses it in around 2 seconds. Handles fiscal classification (Tabaco, Serviços, Sujeito a IVA, Raspadinhas), reconciles against the accountant's Sage balancete, and exports multi-store multi-month xlsx. All money is bigint cents from the moment it leaves the XML.

Case study

Context

Two client retail chains, six stores between them, each store filing SAF-T (Portugal's standard audit file for tax) with the Autoridade Tributária every month. The submission file runs about 50 MB per store per month, with roughly 15,000 invoices and 55,000 line items inside. The previous workflow was a per-file Excel model: import the XML, apply per-line VAT logic, split by fiscal category, reconcile the scratch card commission, cross-check against the accountant's Sage balancete. It worked but it was slow, one file at a time, and it added up to a full day of monthly bookkeeping per client.

Approach

Rewrote the workflow as a web app so parsing and classification happen entirely in the browser.

  • Stream the XML inside a Web Worker, keeping only one document in scope at a time. Progress is reported by bytes read, so a 50 MB file never freezes the UI. Parse time is about 2 seconds per file.
  • Automatic fiscal classification (Faturação líquida, Comissão de raspadinhas, Tabaco, Sujeito a IVA, split between Produtos and Serviços) applied against product taxonomy rules encoded from the practice, with a reviewable UI to correct edge cases.
  • Scratch-card commission apuramento by article and by sale type (CF vs Revenda). Unit facial value, quantities, faturado, and the retained margin per store: what the client books as revenue versus what passes through to Santa Casa.
  • Balancete reconciliation. Upload the accountant's Sage balancete, the tool maps each account (7111112, 711212, 7221112, ...) to (loja × category × VAT rate), cross-references it against the SAF-T aggregate, and produces a Balancete | SAF-T | Diferença matrix with proposed debit/credit journal entries balanced for regularização.
  • Multi-store, multi-month xlsx export in around 10 seconds per year of data.

Engineering notes

  • Streaming XML in a Web Worker. A 50 MB SAF-T can carry 60k+ documents; loading into memory hangs the browser. The parser reads chunks, keeps only one document in scope, and reports progress by bytes. The UI stays responsive throughout.
  • Money in integer cents. 0.1 + 0.2 !== 0.3 breaks reconciliation after 25,000 lines. All money is stored and computed as bigint cents; parsing uses a hand-written decimal-to-integer scaler with half-up rounding to match Excel and AT expectations.
  • Postgres RPCs, not views, for reports. The initial GROUP BY views hit statement_timeout even for a single (store, month) query because the planner didn't push filters through the aggregation. Rewrote as LANGUAGE SQL STABLE functions with WITH ... AS MATERIALIZED CTEs that force the period-first lookup path, and bumped the per-function statement_timeout for the heavier ones.
  • Multi-file period support. AT sometimes splits a month into two files (e.g., 1 to 15 and 16 to 31). Import finds-or-creates the period, dedupes by invoice number, and refuses re-imports of the same file by SHA-256 hash.

Outcome

In production across 2 client companies and 6 stores. The Postgres backing store now holds about 700 MB and 2 million line-level rows, indexed for sub-second dashboard queries.

For one accountant working three stores, monthly bookkeeping collapsed from a full day into about 5 minutes:

Task Manual Excel flow This tool
Import and parse one month 30 to 60 min ~2 s parse plus one click
Classify lines (product, tobacco, services, games) ~1 hour, error-prone Automatic, reviewable
Cross-check with balancete ~2 hours monthly, manual Upload plus instant matrix
Multi-store, multi-month export Not feasible ~10 s per year

Reconciliation also surfaced errors the manual flow was silently missing:

  • Store-level revenue misallocation. The accounting software couldn't split revenue by store, so the accountant had been posting everything to one store's account. Reconciliation surfaced about €90,000 of Turquel sales sitting on the Ermidas ledger in a single month.
  • Service classification bug. A lookup key mismatch was routing all café and bar sales to plain product VAT instead of Prestação de Serviços. Once caught, about €5,000 per store per month shifted to the correct VAT category, correcting the client's monthly VAT declaration.
  • Bar-variant collisions. SAF-T uses a "B" suffix for bar variants of a product (e.g., 1102010101066815B). The normaliser was stripping the B and silently treating bar sales and mercearia sales as the same article.
  • Credit-note double-counting. Scratch cards returned via credit notes were being subtracted twice in reconciliation totals, causing a phantom shortfall.
  • Partial-account exceptions. Accounts like 7221113 (Cafetaria Ermidas 23%) had €1,908 booked but only €14.83 was a legitimate manual adjustment; the rest had to match SAF-T. The tool lets the user mark exceptions with editable amounts.
  • Services-catalog typos. Comparing the client's monthly list of service-classified products against what actually got classified surfaced consistent typos and forgotten items (SUMFRES2/3X, BOL15, SANDES6).

Stack

Next.js 16 (App Router) with React 19 and TypeScript. Streaming SAX parser running inside a Web Worker for the SAF-T XML. ExcelJS for balancete import and multi-store xlsx export. Supabase for Postgres with row-level security, backing about 700 MB and 2 million rows of line-level data. Tailwind CSS. Deployed on Vercel.

Personal project

End-to-end system for Liga Record. A chain of ML models forecasts expected points per player per round (hurdle for P(plays) × E(minutes), match rating, valorização, event probabilities under the official scoring rules), then integer programming in PuLP picks the 23-man squad and starting XI under the €40M budget, 3/8/8/4 position quotas, captain rule, and the real transfer regime. Backtested across two full seasons at ~48 to 51 expected points per round versus a random baseline near 17. Weekly autonomous pipeline on GitHub Actions with 450+ tests.

  • Python
  • Postgres

Case study

Context

Liga Record is Record newspaper's fantasy game for Portugal's Primeira Liga. Each round you manage a 23-man squad and a starting XI under a €40M budget, 3/8/8/4 position quotas, one captain (points doubled), and hard transfer rules (one per round, six in the February window). Scoring blends objective events (goals, clean sheets, cards) with the newspaper's own subjective valorização, which accounts for roughly three quarters of a player's points. Source data is not archived by anyone, so the pipeline had to solve data collection before it could solve the game.

Approach

Two connected pieces: a chain of forecasts, then an optimiser under the real rules of the game.

Forecasts. Points per player per round come from a chain, not a single model:

  • Hurdle for participation: P(plays) × E(minutes given plays).
  • Match-rating model per player-fixture.
  • A model for valorização, the subjective score that carries roughly three quarters of a player's points.
  • Event probability components (goals, clean sheets, cards) combined through the official scoring rules.
  • Fixture difficulty from a Dixon-Coles team-strength model, blended with live betting-market odds.

Optimiser. The forecasts feed an integer program in PuLP that maximises expected total points for the round subject to every real rule: €40M budget, 3/8/8/4 quotas, valid formation, one captain with points doubled, and the transfer regime with wallet accounting. Output is a suggested XI and bench plus a diff against the current squad.

Engineering notes

  • Leakage discipline. Features are computed against the round's deadline as a time boundary, not the round number. A naive by-round implementation was silently pulling future information into 38.7% of training games. A second, subtler look-ahead lived in the squad-selection horizon and was worth about 6 pts/round; caught in a self-audit and fixed by freezing form at each decision deadline.
  • Honest evaluation over a tempting result. Concentrating the budget on the starting XI looked like +6 pts/round on a single season. Validating out-of-sample on a second season showed it was overfitting, so the simpler baseline stayed. Not shipping a lucky number is part of the model too.
  • Dead code paths surfaced by the audit. Betting-market odds were being computed but never actually consumed by the forecast (+2.55 pts/round once wired in). Adding each player's own past-score history as a feature added another +0.98.

Outcome

Backtested across two full seasons (2024/25 and 2025/26) with a leakage-free pipeline:

  • ~48 to 51 expected points per round, capturing about 44% of a perfect-hindsight ideal. Stable across both seasons.
  • +31 pts/round versus a random-selection baseline.
  • +18 pts/round versus a most-minutes heuristic.
  • 450+ tests, weekly autonomous pipeline on GitHub Actions.

Reported as expected points in backtesting and replay, not live winnings. The system is a decision aid.

Stack

Python 3.11. Modelling with scikit-learn (gradient-boosted trees), NumPy, SciPy, and a Dixon-Coles football model. PuLP for the integer program. PostgreSQL via Supabase, psycopg v3. Data from API-Football, football-data.co.uk, and the official Liga Record newsletter and spreadsheets. Web app in Next.js 15 (App Router, React server components) and TypeScript on Vercel. GitHub Actions for the weekly cron. ruff and pytest (450+ tests).

Private, mobile-first stock and sales manager for a Portuguese used-car dealership. One auth-gated dashboard covers each car's full lifecycle: acquisition, reconditioning expenses, sale, and VAT settlement under the correct Portuguese regime (Regime da Margem or Regime Geral). On sale, a plaintext summary of acquisition, expenses, sale, VAT, and net result is emailed to the accountant automatically. European Portuguese UI, built to be used on a phone while walking the lot.

Case study

Context

Small Portuguese used-car dealerships (stands) run on paper folders, WhatsApp photos, and Excel. Every vehicle carries a growing pile of costs (mechanic, painting, IPO inspection, ISV legalisation, tyres, detailing, transport) and each sale has to be booked under one of two very different VAT regimes: Regime da Margem (VAT on the margin only, common for cars bought from private sellers) or Regime Geral (VAT on the full sale price). Choose the wrong regime or misplace an expense receipt and you either pay tax you didn't owe or miss tax you did. The dealer wanted one place to see stock, running cost per car, days in stock, and a live per-vehicle P&L that already applied the correct regime.

Approach

One private, auth-gated app that owns the full lifecycle of a car from intake to sale:

  • Painel. Four live KPIs (cars in stock, immobilised capital, average margin, monthly sales) and a sortable stock table with per-vehicle expense totals.
  • Vehicle intake. Full record: plate, VIN, brand and model and version, mileage, fuel, purchase date and price, supplier type (particular, stand, auction, company), NIF, VAT regime, and the scanned purchase document.
  • Expenses tracker. Typed entries (mechanical, bodywork, tyres, IPO, ISV, transport, commission, detailing) with a deductible-VAT flag and a document upload, each attached to a specific vehicle.
  • Sale registration and apuramento. Records the sale and instantly computes margem tributável, IVA apurado at 23%, total costs, days in stock, and the net result. Green or red on the bottom line.
  • Automated sale email. On sale creation a plaintext summary (acquisition, all expenses, sale, VAT, result) is sent to the office inbox via Resend and the sale is stamped as email_enviado.

The UI is entirely in European Portuguese (Painel, Viaturas, Despesas, Apuramento, Fornecedor, Matrícula) and mobile-first. The dealer opens it on a phone while walking the lot.

Engineering notes

  • One pure tax function. calcularApuramento() is a small, tested pure function that implements both Portuguese regimes correctly. It's called identically from the dashboard aggregate, the vehicle detail view, and the sale API route. The regime logic exists in exactly one place.
  • Server-first rendering. Dashboard and vehicle detail pages are async React Server Components fetching directly from Supabase, so the initial paint already has data.

Case study

Context

The Autoridade Tributária requires every business to submit a SAF-T PT invoice file every month. Before the app, doing this across the practice's clients meant, for each one: open the Excel with the client's NIF and password, log in to Portal das Finanças, click through several pages to the SAF-T submission form, pick year and month, browse the file system for the right XML, upload, wait, verify the confirmation. Close the session, back to the Excel, repeat for the next client. Around 3 to 5 minutes per submission when the portal cooperated, longer when it did not, and the only audit trail was whatever the accountant wrote down by hand.

Approach

A Streamlit frontend around FACTEMICLI, the AT's Java CLI for SAF-T submissions. The CLI is a scriptable alternative to the portal, but on its own it means typing a 60-character command with credentials, paths, and period flags every time. The app never replaces the official binary; it makes it usable.

  • Client registry as a local JSON store. Adding a client (name, NIF, password) once means picking them from a dropdown ever after. NIF is validated on entry: 9 digits, no duplicates.
  • Year and month pickers default to the current period, which is the right choice almost every time.
  • XML uploader, then a single "Executar Envio" button assembles the full java -jar command with the right flags and runs it as a subprocess with captured stdout and stderr.
  • The AT's response file is parsed as XML instead of dumped as-is. The tool pulls out the status code, totalFaturas, totalCreditos, totalDebitos, and any error message inside <errors><error>, then renders success or failure with the numbers front and centre.
  • Every submission is appended to a CSV log: timestamp, client, NIF, period, filename, success flag, response code, message, and the three totals. One file, sortable in Excel, complete history.

Engineering notes

  • Latin-1 responses. The AT tool writes its result file in latin-1, not UTF-8. Decoding as UTF-8 corrupts the error messages, so the reader opens with encoding="latin1" explicitly.
  • Subprocess with graceful failure. If the jar exits non-zero, the CalledProcessError is caught and stderr is written into the result file so the user still sees what happened. The XML parser falls through to a "could not interpret response" state instead of crashing the app.
  • Structured logging over shell history. The CSV header is written once on file creation; every subsequent submission appends a row. Nothing to configure, nothing to click.
  • Zero credential re-entry. Passwords sit in the JSON registry alongside the NIF. Trade-off: the file is local to the accountant's machine, but it saves typing (or pasting from a text file) on every submission.
  • Sensible period defaults. The year dropdown covers the current year and the previous five; the month defaults to the current month. Historical resubmissions still work, but the common case is one click.
  • Scoped, disposable temp directory. Uploaded XML and AT responses live under temp/, nothing else survives a session.

Outcome

In monthly production use across the practice. Per-submission time dropped from around 4 minutes on the portal to under 30 seconds in the app. About 3.5 minutes saved per client per month. Across the practice's 40-client book, that is roughly 2h20 back every month, or close to 28 hours a year. Failed submissions carry the AT's error code and message straight into the CSV log, so retries can be triaged without redoing the whole portal flow. "Did we submit for client X in April?" goes from a portal login to a Ctrl+F.

// RLS-first schema, rank at read time, namespace-agnostic .xlsx parser

  • Next.js 16
  • React 19
  • TypeScript
  • Supabase
  • Tailwind v4
Case study

Context

A friends' Fantasy Record league had grown to around 20 players and was being run out of a WhatsApp group and a shared Excel. Whoever landed first place each round was owed €0.10 per point of difference by everyone else, plus a side bet, plus a running tab for the end-of-season dinner. Every week the admin was doing the math by hand and chasing people to pay. The app takes the weekly Excel export from Fantasy Record and turns it into a live dashboard, a cup with a random group draw, a 1-X-2 betting flow with penalties, and a single accounting view.

Approach

Six connected surfaces built on one authorised Postgres schema:

  • Dashboard. Round points, cumulative total, current league position, money-owed tile, and a form chart (SVG line, dual series: you vs the round winner, clickable per round).
  • Classificação. General league table plus a per-round view, both with abbreviated mobile-first columns.
  • Taça. Cup running in parallel. 4 groups of 5 with a random draw button (admin), Fase de Grupos, Oitavos, Quartos, Meias, Final. Top 4 of each group advance, current phase is highlighted.
  • Apostas. Admin creates a slate (name, deadline, up to 4 games as 1-X-2). Each player picks. After the deadline the scoring rule kicks in: 0€ if all correct, 0.50€ per wrong pick, 1€ if the player didn't pick at all. Every open slate has a "Partilhar no WhatsApp" button that opens the composer pre-filled with the formatted announcement.
  • Contabilidade. Carryover from last season (admin-editable), current-season pot (auto-summed from rounds and settled slates), dinner budget (admin-editable), available balance. Full player × round × slate breakdown matrix with a totals row.
  • Admin. Excel upload (custom parser that survives the Fantasy Record namespace prefix), team CRUD, slate and game CRUD, cup draw.

Login is Supabase Auth restricted to email addresses the admin has whitelisted by mapping them to a team row. The whole UI is European Portuguese.

Engineering notes

  • RLS-first authorisation. Every table is authorised by row-level security in the database, not at the app layer. Two SECURITY DEFINER helpers, public.is_admin() and public.my_team_id(), break the recursion that would otherwise happen when policies on the teams table query the teams table, and give clean predicates like team_id = my_team_id() or is_admin() on write policies.
  • Rank at read time, not at write time. Positions aren't stored. Sorting a team's points_round against every other team happens in the query at request time, so the leaderboard is always correct even if the Excel loaded a stale global position. Standard-competition ranking (ties share a rank) lives in one assignRanks<T>() utility.
  • Namespace-agnostic .xlsx parser. The Fantasy Record export uses the x: XML namespace prefix on every element (<x:sheets>, <x:worksheet>), which broke off-the-shelf libraries. Dropped exceljs (which choked on the prefix and carried a uuid sub-dep advisory) and wrote a small parser: JSZip to unzip the file, a namespace-agnostic regex over the sheet XML to extract the rows. Smaller bundle, no known vulns.
  • Feature-scoped SQL migrations. Each vertical (cup, accounting, bet slates) ships with its own idempotent migration file alongside a schema.sql that re-derives the same tables from scratch. The RLS reset lives in dedicated helpers so migrations are safe to re-run without dropping data.
  • Design-token overrides, no component rewrites. The shift from a generic dark-slate palette to warm charcoal with camel accents on a stadium photo background was done by remapping Tailwind's slate-* and emerald-* scales inside @theme, not by editing 20+ components. Adding new colours is a diff in one CSS file.
  • middleware.ts to proxy.ts. Next.js 16 renamed the file. Session refresh and route protection were migrated to the new proxy convention as part of the initial scaffold.
