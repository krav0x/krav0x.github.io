Campo de Padel

The parish had one padel court and no booking system — slots were handled by phone and by walking into the office. This platform replaces that with authenticated web bookings against a Postgres bookings table. Users pick from 30 fixed start times (every 30 minutes, 08:00–22:30), each locked to a 90-minute duration; the server rejects any insert whose interval overlaps an existing row on the same date. A 2-per-day per-user quota is enforced in the server action, and a sentinel user_id marks slots blocked by the admin for maintenance. An Open-Meteo call annotates each slot with temperature, wind, and rain probability so residents can see conditions before confirming. Auth is Supabase, by email/password or Google OAuth; a Supabase Edge Function sends the confirmation email after a successful insert.

Next.js 16.2.7 React 19.2.7 Supabase @supabase/ssr 0.10.3 TypeScript 5 Tailwind CSS 4

01 · Context

Context

The Junta de Freguesia de Ermidas-Sado, a parish council in Alentejo, Portugal, runs a single padel court open to residents. Before this platform there was no digital booking — reservations went through phone calls to the parish office and a paper agenda, which meant no visibility outside office hours, no way to enforce fair per-user quotas, and no self-service cancellation.

The people booking are neighbours of a small rural parish, not padel-club regulars, so the whole UI is in Portuguese, uses parish branding, and keeps the per-slot decisions — rain, wind, time already passed — visible at a glance.

02 · Approach

Approach

One Next.js App Router page hosts the whole booking surface: a date strip for the next seven days, a grid of 30 half-hour start times per day, and, for the admin, an executive panel with occupancy stats. The rules the system actually encodes:

  • Fixed 90-minute slots. Every booking is exactly startTime + 90 min; duration is not user-selectable.
  • Grid of 30 start times per day, 08:00 to 22:30 in 30-minute steps.
  • Overlap prevention. A booking is rejected server-side if any existing row on the same date satisfies start_time < newEnd AND end_time > newStart.
  • Per-user daily quota. A regular user is blocked at 2 bookings on the same booking_date.
  • Past-slot filtering. For today the grid hides any slot whose start time has already passed, and elapsed bookings are stripped from the upcoming-games list.
  • Admin maintenance blocks. The admin can mark a slot as Bloqueio Técnico; the insert uses a reserved zero-UUID as user_id, and the slot renders in red until it is released.
  • Weather annotation. Each cell fetches the hourly forecast from Open-Meteo (lat 38.0264, lon −8.3619, Europe/Lisbon) and colours the cell when rain probability reaches 40% or wind reaches 20 km/h. The confirm button changes wording — Reservar com Chuva, Reservar com Vento — but does not block the booking.
  • Confirmation email. After a successful non-maintenance insert, the server action invokes a Supabase Edge Function send-email with the user's email, date, and time.

03 · Engineering notes

Engineering notes

  • Schema. Two tables in Supabase: bookings (id, user_id, booking_date, start_time, end_time) and profiles (id, full_name). Times are stored as Postgres time values and the date as date. No SQL migrations are checked in — the schema lives in the linked Supabase project only, so a full rebuild currently needs the dashboard rather than the repo.
  • The overlap check is not race-safe. The conflict check is a SELECT followed by an INSERT in two round trips, so two simultaneous bookings for the same slot can both see an empty conflict set and both insert. The right fix is a Postgres exclusion constraint over tstzrange, or a unique constraint on (booking_date, start_time) given the fixed grid. Not in place today.
  • Admin identity is hardcoded. isAdmin is a string comparison against a fixed email address, in both the page and the server action. Moving it to a role column on profiles is the obvious next step.
  • Row-level security. Cancellation is scoped by .eq('user_id', userId) for non-admins, so a user cannot delete someone else's row through the server action. That guard is defence in depth rather than the primary boundary — it should also be enforced with Postgres RLS on bookings.
  • Timezone and DST. Date keys come from new Date().toISOString().split('T')[0] in the browser, which returns the UTC date rather than the Europe/Lisbon one. Late-evening bookings while Lisbon is on WEST can therefore land on the next day's key. Not currently fixed.
  • Auth. Supabase email/password plus a Google OAuth flow routed through /auth/callback, a server route that exchanges the code for a session. SSR session handling uses @supabase/ssr with cookie plumbing in src/lib/supabase/server.ts.
  • Tests. None. Correctness is currently only exercised by hand.
  • Scheduled jobs. None. The confirmation email is invoked inline; there is no reminder or cleanup job.

04 · Outcome

Outcome

What works end to end today: sign-up and sign-in by email or Google, booking against the 30-slot grid with overlap and quota rejection, self-cancellation, admin maintenance blocks, per-slot weather annotation, and a confirmation email through a Supabase Edge Function.

05 · Stack

Stack

  • Framework. Next.js 16.2.7 with the App Router, Server Actions and next/font Geist; React 19.2.7; TypeScript 5.
  • Backend and data. Supabase — Postgres (bookings, profiles), Supabase Auth (email/password and Google OAuth), Supabase Edge Functions (send-email), and @supabase/ssr 0.10.3 for cookie-based server sessions.
  • Styling. Tailwind CSS 4 with @tailwindcss/postcss; glassmorphism surfaces over a fixed gradient backdrop; light and dark themes with a manual toggle and a pre-hydration inline script to avoid the flash.
  • External APIs. Open-Meteo hourly forecast, no key required.
  • Language and locale. UI in Portuguese (pt-PT), dates and weekdays formatted through toLocaleDateString('pt-PT', …).
  • Deploy. Intended for Vercel-style Next.js hosting; no CI or infrastructure-as-code checked in.

06 · Roadmap

Roadmap

  • Replace the select-then-insert overlap check with a Postgres exclusion constraint over the [start_time, end_time) interval per booking_date.
  • Move admin identity from a hardcoded email to a role column, and enforce bookings and cancellations with RLS.
  • Compute date keys in Europe/Lisbon rather than UTC, so late-evening slots do not roll to the next day.
  • Check the migration set into the repository under supabase/migrations, so the schema is reproducible outside the linked project.
