WIP, retrieval baseline shipping

Portuguese Accounting RAG

Portuguese-language RAG assistant over Portugal's core tax and accounting corpus (CIRS, CIRC, CIVA, RITI, LGT, EBF, SNC, NCRF). 4,448 article-level chunks embedded once with multilingual-e5-large, stored in Chroma, queried via MiniMax M3 on OpenRouter. The prompt hard-codes three rules: answer only from retrieved context, cite the specific article, refuse otherwise. Retrieval iteration moved recall@5 from 47.6% to 61.9% under a strict tuple-based grader on a 25-question held-out eval; 100% refusal accuracy on the 4 refuse-worthy questions; 9.5% hallucination rate on the baseline. Tier-1 (read-only lookup) only in the current build.

RAG LangChain ChromaDB MiniMax M3 Streamlit Portuguese NLP

01 · Context

Context

Practising Portuguese accountants and business owners keep asking the same class of question: "which article covers this?", "what's the rate on X?", "how is Y treated for VAT?". The correct answers live in a few thousand pages of primary legislation (Códigos, Decretos-Lei, NCRF standards) that a general-purpose LLM will happily paraphrase from memory, often with a confident but wrong article number. The bar this project sets for itself is narrower than "an accountant in a box": produce an answer in European Portuguese that is (a) traceable to a specific article of a specific code and (b) explicitly refuses when the retrieved context doesn't support the question, so the user knows to escalate instead of trusting a fabrication.

02 · Approach

Approach

Single-tier RAG, deliberately kept simple:

  • Knowledge layer, RAG. Primary legislation is chunked article-by-article for the tax codes (Artigo N.º boundary regex) and by recursive character splitting for the accounting standards (NCRF, EC, NI, SNC), which don't follow a strict article structure. Chunks are embedded once with intfloat/multilingual-e5-large and stored in a persistent Chroma collection.
  • Behaviour layer, prompt only. No LoRA. The behaviour of the assistant (answer in European Portuguese, only from retrieved context, cite the article, refuse otherwise) is enforced entirely in the system prompt. A LoRA pass was scoped but not run; the choice was to see how far a strong instruction-tuned base could go on a well-chunked corpus before spending on adapter training.
  • Computation layer, none yet. The current build does no deterministic numeric computation. Questions that ask "how much would I pay" are treated as refusal cases and pushed back to the user with a "consult a certified accountant" recommendation.

Autonomy tiers. The design target is three tiers: (1) read-only lookup, (2) draft-and-review with a human accountant approving, (3) prepare-for-submission with structured outputs for AT portals. The current build only implements tier 1; the eval below is scored against that scope.

Model choice. The app now serves MiniMax M3 via OpenRouter's free tier. Groq had decommissioned llama-3.3-70b-versatile mid-project, and MiniMax was the strongest currently-free Portuguese-capable model on OpenRouter (1M-token context, clean European Portuguese output). Earlier retrieval-iteration runs used Llama-3.3-70B via Groq and then via the Hugging Face inference router until those credits also ran out; recall numbers don't depend on the LLM so they're comparable across the swap.

04 · Engineering notes

Engineering notes

  • Hybrid chunker. split_by_article_strict uses a (?i)(Artigo\s+\d+\.º(?:-[A-Z])?) regex on the tax codes so every chunk is one legal article with its number in the chunk id ("CIVA - Artigo 18.º"). NCRF, EC, NI use a 1000/100 recursive splitter because those documents don't have article-level structure. This is what makes citations traceable: the retrieved chunk id is the citation.
  • Multilingual embedding choice. intfloat/multilingual-e5-large was picked over Portuguese-only encoders because the corpus mixes technical Portuguese (legislative style), abbreviations (IRS, IVA, PPR), and code numbers. E5-large was empirically better at surfacing the correct article across the eval set than smaller multilingual MiniLM variants tested locally.
  • Retrieval-tight prompt. The prompt hard-codes three rules (answer only from context, refuse otherwise, respond in European Portuguese). Every one of the 4 refusal-worthy questions in the eval produced a proper refusal, and the model correctly refused on retrieval misses instead of hallucinating a number.
  • Streamlit UI with citation panel. Every answer ships with a "View Sources / Legal Basis" panel that dumps chunk id and a 300-character preview per retrieved doc, so the user can verify the citation without leaving the tab.
  • What is not in there. No LangGraph, no agentic tool use, no LoRA, no query decomposition. Those are candidates for later iterations; none are implemented today, and I would rather be measured on what is shipped than on what is planned.

05 · Evaluation setup

Evaluation setup

25-question held-out eval set: 18 single-source factual lookups, 3 cross-source questions that require chunks from two codes, 4 refusal-worthy questions (personal legal advice, personalised numeric computation, post-cutoff regulatory data, cross-border tax planning). Ground-truth citations are stored per question in evals/eval_set.json; a lightweight harness (evals/run_eval.py, evals/eval_retrieval.py) queries the live Chroma store, runs the same prompt the app uses, and auto-grades each answer.

Auto-grader rubric (a proxy for hand-grading, not a substitute):

  • Retrieval hit @k. The expected article id and any retrieved chunk id both canonicalise to the same (SOURCE, N, SUFFIX?) tuple, within the top-k. Strict boundary matching, so Artigo 68 and Artigo 68-A are distinct. An earlier draft used substring matching, which was flattering every recall number by ~10 pts at @5.
  • Answer accuracy. The answer contains at least min_keyword_hits of the pre-declared correctness keywords.
  • Hallucination. The answer cites an Artigo N.º that does not appear in any of the retrieved chunks fed to the LLM.
  • Refusal correctness. For the 4 refuse-questions, the answer matches one of the refusal-phrase patterns.

06 · Outcome

Outcome

Retrieval was iterated on because it caps everything downstream. Every row below is a real, reproducible run of evals/eval_retrieval.py against the eval set.

Retrieval recall (n=21 non-refuse questions):

Config@1@3@5@10
v1 baseline (raw chunks, no prefix)19.0%33.3%47.6%66.7%
v2, E5 "query:" / "passage:" prefixes23.8%52.4%57.1%61.9%
v3, v2 + source-tag headers (chosen)28.6%52.4%61.9%71.4%
v4, aggressive dedup (1 chunk / article)9.5%33.3%38.1%38.1%
v5, filter-only + source-tag + E5 prefix19.0%42.9%57.1%71.4%

v5 + bge-reranker-v2-m3 cross-encoder33.3%47.6%61.9%71.4%

+14.3 points of recall@5 vs the v1 baseline, the metric that actually decides whether the LLM sees the correct article. v3 (source-tagged, all substantive chunks kept) beats v5 (filtered): the "drop TOC noise" step was marginally hurting more than helping, so v5 was reverted.

What each iteration changed:

  • v2, E5 prefixes on both sides. intfloat/multilingual-e5-large was trained with "query: " in front of queries and "passage: " in front of documents. Re-indexing with the "passage: " prefix and prepending "query: " at retrieval time is a documented free lift. Result: +5 pts on @1 and @3.
  • v3, source-tag headers in the embedded text. The chunker was writing the source name into chunk metadata, but not into the embedded text. A query mentioning "IRC" had no lexical anchor to the CIRC chunks; it had to match through semantics alone. Fix: prepend "[CIVA] CIVA - Artigo 18" to each chunk's text before embedding. Result: +4.8 pts on top of v2, bringing the total baseline-to-v3 lift to +14.3 pts.
  • v4, over-eager dedup (backed out). CIVA-Artigo 2 was fragmented into 141 chunks, CIVA-Artigo 3 into 109, because the PDFs open with a full table of contents and inline-reference each article dozens of times. Keeping only the longest fragment per article dropped recall@5 to 38.1%: for CIVA-18, the longest fragment carried grouped-goods rules, not the rate table with 23%. Reverted.
  • v5, filter, don't dedup (tried, reverted). Dropped chunks that were mostly dot-leaders (TOC entries) or shorter than 120 non-dot characters. Corpus went from 4,448 to 3,211 substantive chunks. Result under the strict grader: −4.8 pts at recall@5 vs v3. A few of the "TOC-looking" chunks actually carried answers.
  • BM25 hybrid (tried, didn't ship). Portuguese legal text saturates BM25 with high-frequency generic phrases. RRF fusion at four different weightings; none beat dense-alone.
  • Cross-encoder reranking (tried, didn't ship). BAAI/bge-reranker-v2-m3 over a pool of 30 dense hits. +5 pts at recall@1 but hurt @3 and @5. On CPU it added ~38 s per query, a non-starter for a Streamlit tool.

07 · Failure modes and confounds

Failure modes and confounds

Six of the 21 non-refuse questions never enter top-10 across any tried config:

  • Q02. "Qual é a taxa geral do IVA em Portugal continental?" (target CIVA-Artigo 18).
  • Q03. "Qual é a taxa geral do IRC aplicável a sujeitos passivos residentes?" (target CIRC-Artigo 87).
  • Q12. "Em que consiste o regime do IRS Jovem?" (target CIRS-Artigo 12-B).
  • Q17. "Como se determina o lucro tributável em sede de IRC?" (target CIRC-Artigo 17).
  • Q19. Cross-code (CIRS-31 + CIRC-17).
  • Q20. Cross-code (CIVA-3 + CIRC-23).

Manual inspection confirmed the answer text is in the corpus: CIVA-18 fragment #4 literally contains "a taxa de 23 %". Dense retrieval isn't finding them because the queries use paraphrases the chunks don't contain. "taxa geral" and "sujeitos passivos residentes" in the query semantically match articles about regime geral and residência fiscal, not the rate table. That is a query-side problem, not a retriever-side one.

There is also an upstream PDF-extraction issue: for a few CIVA articles, PyMuPDF loses the multi-column rate tables entirely. That is a floor on retrieval quality no encoder tuning can lift.

Confounds worth stating out loud:

  • n=25 is small. A real portfolio-grade eval wants 100+ items with inter-annotator agreement on citations.
  • Keyword auto-grading misses correct paraphrases; a stronger judge model would give a more defensible answer-accuracy figure.
  • I graded my own eval. The retrieval and refusal numbers, which don't depend on the grader, would not move.
  • Ground truth had to be corrected mid-run when the actual PDFs cited Lei n.º 64/2025 (IRC to 17%, first-50k to 15%). This is why an assistant that refuses a memorised answer is more valuable than one that confidently recites an out-of-date figure.
  • Only one base model was evaluated. Amália (EuroLLM-9B) and EuroLLM-22B were scoped for an A/B but neither is wired up in the current build.

08 · Roadmap

Roadmap

Portfolio-shippable target is ≥80% recall@5. Two concrete levers, in priority order:

  • Query rewriter. A small LLM step that reformulates the user's question into 2 or 3 lexical variants and OR-s the results. Best guess: +10 to 15 pts of recall@5.
  • PDF extraction pass. Swap PyMuPDF for pdfplumber with a table-aware extractor to recover the CIVA rate tables. Lifts a floor rather than a ceiling; helps only a few questions, but they are unrecoverable today.

Longer-horizon:

  • AT circulars and OE annual updates in the corpus, with per-chunk validity dates so refusals can be precise.
  • Tier-2 autonomy path: a draft-a-reply mode where the assistant produces a structured citation table a human accountant can approve or reject.
  • Grow the eval to 100 items and run under an LLM-as-judge with a stronger reference model, plus a small A/B against EuroLLM-9B on the same set.

09 · Stack

Stack

Base model (app): MiniMax M3 via OpenRouter free tier, temperature 0.1. Earlier eval runs used Llama-3.3-70B-Instruct via Groq and then via the HF inference router. Embedding: intfloat/multilingual-e5-large, run locally on CPU. RAG store: ChromaDB, persistent on disk, ~47 MB per index. Framework: LangChain (langchain_chroma, langchain_huggingface, langchain_openai, langchain_text_splitters) for the retrieval and prompt-templating glue (OpenRouter is OpenAI-compatible); PyMuPDF (fitz) for PDF extraction. UI: Streamlit. Deployment target: Docker container for a single-container Streamlit deploy on Fly.io or Render.

Portuguese-language notes. UI and prompts use PT-PT throughout (declaração, coleta, matéria coletável, sujeito passivo, isenção, tributação autónoma), not the Brazilian variants a general LLM would default to. The chunker preserves the ordinal marker (Artigo 68.º) so the retrieved citation reads correctly in the legal-Portuguese convention. The refusal path is phrased as a formal recommendation ("recomendo consultar um contabilista certificado") rather than a shrug.
